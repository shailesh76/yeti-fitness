# Yeti Exercise Library — Architecture & Specifications

## Overview

The **Yeti Exercise Library** serves as the canonical first-party source of truth for exercises across workouts, AI coaching, exercise search, and workout building in the Yeti Fitness platform.

---

## 1. Canonical Source Taxonomy

All exercises in `public.exercises` are classified under one of three canonical `source_type` values:

| `source_type` | Description | Count |
|---|---|---|
| `yeti_first_party` | Official Yeti-owned exercises (V2 equipment + V3 expansion catalog) | 396 live (420 total dataset items) |
| `legacy_catalog` | Pre-existing imported exercises from external sources (`free-exercise-db`, `omercotkd-gifs`, etc.) | 2095 live |
| `custom` | Coach-created custom exercises | Dynamic |

> **Dataset Provenance**: Dataset versions are annotated in the `metadata` JSONB column as an **array**, e.g. `{"dataset_version": ["v2"]}` or `{"dataset_version": ["v2","v3"]}` for a merged exercise, alongside `{"content_source": "v3"}` naming the dataset that supplies the content. Provenance is never encoded as extra `source_type` values.

### Source records vs canonical exercises

The two datasets contain **420 source records** (V2: 220, V3: 200), but the catalogue holds **396 canonical exercises**. The numbers differ because **24 slugs appear in both datasets** and describe the same exercise, so each pair reconciles to a single row:

```
220 (V2) + 200 (V3) − 24 (shared slugs) = 396 canonical exercises
```

Not all 420 records become separate database rows. Membership is derived only from the checked-in datasets via the provenance manifest — never from `source_type` (which carries a permissive column default) and never from ID shape (V2 dataset ids such as `yeti-ex-0001` are not UUIDs, so the importer minted UUIDs for them).

### Merge-winner strategy

For each of the 24 shared slugs, **V3 supplies the content**. This is recorded explicitly as `merge_winner` in the manifest so the outcome never depends on which file is imported last. The evidence:

- V2's `execution_instructions` are boilerplate — only **2 distinct strings across 220 records**, one reused 208 times — while V3 has 200 distinct strings for 200 records.
- V2's `primary_muscle` is often a category default rather than the working muscle: "Quadriceps" is recorded for Cable Glute Kickback, Cable Pull-Through *and* Smith Machine Hip Thrust.
- V3 is the later, taxonomy-normalised pass and corrects those values.

Import order previously decided this implicitly, and decided it wrongly: **22 of the 24 live rows currently hold V2 content and none hold V3.** Re-importing V3 under the manifest is what corrects them, updating each row in place so its UUID — and every `plan_exercises` / `session_sets` reference to it — survives.

### Provenance manifest

`scripts/data/yeti_exercise_provenance.json` is generated by `scripts/generate_exercise_provenance.ts` and is the single source of canonical membership. It also emits the SQL manifest block embedded in the taxonomy migration, so the two cannot drift; `--check` fails if they do.

```bash
npx tsx scripts/generate_exercise_provenance.ts          # regenerate
npx tsx scripts/generate_exercise_provenance.ts --check  # verify in sync
```

### Live state (pre-reconciliation, verified)

At the time of writing, before `20260812133000` is applied: **396 rows carry `source_type = 'yeti_v2'` and 2095 carry `legacy_catalog`** (2491 total, 0 custom). All 396 match canonical manifest slugs exactly, with no contaminated rows and none missing.

## 2. Database Schema

The exercise library extends `public.exercises` and includes 7 normalized sub-tables.

### `public.exercises` Extended Schema
- **`slug`** (`TEXT UNIQUE`): Human-readable URL identifier slug.
- **`primary_muscle`** (`TEXT`): Primary target muscle group (e.g. `Chest`, `Quadriceps`, `Lats`).
- **`movement_pattern`** (`TEXT`): Fundamental movement classification (`Squat`, `Hinge`, `Horizontal Push`, `Horizontal Pull`, `Vertical Push`, `Vertical Pull`, `Lunge`, `Carry`, `Rotation`, `Isolation`).
- **`unilateral`** (`BOOLEAN DEFAULT false`): Single-limb execution flag.
- **`setup_instructions`** (`TEXT`): Equipment & stance positioning.
- **`execution_instructions`** (`TEXT`): Concentric & eccentric instructions.
- **`breathing`** (`TEXT`): Inhalation/exhalation breathing cues.
- **`coaching_cues`** (`TEXT[]`): Key form checkpoints.
- **`common_mistakes`** (`TEXT[]`): Technical errors & fixes.
- **`safety_notes`** (`TEXT`): Injury precautions.
- **`default_sets`** (`INTEGER DEFAULT 3`): Default set count.
- **`default_reps`** (`INTEGER DEFAULT 10`): Numeric compatibility/executable fallback.
- **`default_reps_prescription`** (`TEXT NULL`): Lossless authored display prescription. Ranges and durations are not executable rep counts.
- **`tempo`** (`TEXT DEFAULT '2-0-2-0'`): Timing pattern.
- **`source_type`** (`TEXT`, live DEFAULT `'yeti_v2'`; becomes `'legacy_catalog'` when 20260812133000 is applied): Canonical source classification (`yeti_first_party`, `legacy_catalog`, `custom`).
- **`license`** (`TEXT`): Ownership license terms.
- **`media_status`** (`TEXT DEFAULT 'TO_CREATE'`): Production lifecycle state (`TO_CREATE`, `IN_PROGRESS`, `READY`, `REJECTED`).
- **`media_notes`** (`TEXT`): Filming and angle specifications.
- **`recommended_rest_seconds`** (`INTEGER`): Rest interval.
- **`hypertrophy_reps`** (`TEXT`), **`strength_reps`** (`TEXT`), **`endurance_reps`** (`TEXT`): Target rep ranges per goal.
- **`metadata`** (`JSONB`): Dataset provenance and extra metadata.

### Relational Sub-Tables
1. **`exercise_media`**: Cloudflare R2 media metadata (`exercise_id`, `media_type`, `file_format`, `r2_bucket`, `r2_key`, `url`, `thumbnail_url`, `is_primary`, `media_status`, `media_notes`).
2. **`exercise_aliases`**: Alternative names and search synonyms.
3. **`exercise_tags`**: AI coaching and functional taxonomy tags.
4. **`exercise_muscles`**: Granular muscle involvement map (`primary`, `secondary`, `stabilizer`).
5. **`exercise_alternatives`**: Biomechanically equivalent substitute exercises.
6. **`exercise_progressions`**: Step-up difficulty progressions.
7. **`exercise_regressions`**: Step-down difficulty regressions.

## 3. Exercise Importer Security & CLI

Script: `scripts/import_exercises.ts`

Class: `ExerciseImporter`

Supports importing JSON and CSV exercise datasets with automatic deduplication.

### Security Requirements
- Requires `SUPABASE_SERVICE_ROLE_KEY` for live DB imports.
- Zero embedded user credentials (`signInWithPassword` is strictly prohibited).
- Dry-run validation (`--dry-run`) does not connect to the live database or require credentials.

Usage:
```bash
# Dry-run validation
npx tsx scripts/import_exercises.ts packages/database/seeds/exercises/yeti_equipment_exercises_v2.json --dry-run

# Dataset validation suite
npx tsx scripts/validate_exercise_datasets.ts --dry-run

# Live import (requires service role key env var)
SUPABASE_SERVICE_ROLE_KEY=your_key npx tsx scripts/import_exercises.ts packages/database/seeds/exercises/yeti_equipment_exercises_v2.json
```

## 4. Known Issues & Future Work

- **Dual-field migration is pending deployment** — `default_reps` remains INTEGER for installed-client compatibility. `20260814120000_exercise_default_reps_prescription.sql` additively introduces lossless display text after the Watermelon v8 client ships. Duration prescriptions must never be interpreted as repetitions.

  The importer preserves the original in `metadata.default_reps_authored`; the new column backfill prefers canonical generated data, then authored metadata, then numeric fallback. The unsafe and unapplied `20260812140000_exercise_default_reps_lossless.sql` is preserved for reference under `docs/archive/unsafe-migrations/`, outside the active Supabase migration chain.
- **Support Table Sync**: WatermelonDB offline pull-sync currently covers `exercises` only. Pull-sync for the 7 relational sub-tables is **not implemented** and is scheduled for Round 2, together with Watermelon schema migration 9. No offline guarantee should be assumed for sub-table data today.
- **Media management**: media manager UI and media ordering are **not implemented**; `exercise_media` rows are written by the importer only.
